# R9700 Phase 3 — RDNA INT4 MoE repack result

Date: 2026-09-11

## Status

**C4 FULL-MODEL KEEP / SMALL-M + LONG-CONTEXT OPTIMIZATION OPEN / PRODUCTION PROMOTION PENDING STABILITY GATE**

## Pre-serving correctness gates

The patch applies cleanly to the ROCm10 vLLM source and all five patched modules compile. Synthetic layout tests verified exact INT4 repack and zero-point unpack behavior.

Real Qwen layer-0 AutoAWQ weights were then tested before full-model serving:

- gate projection: qweight `[2048,96]`, qzeros `[16,96]`, scales `[16,768]`, group size 128;
- down projection: qweight `[768,256]`, qzeros `[6,256]`, scales `[6,2048]`, group size 128;
- weight repack exact: PASS/PASS;
- zero-point conversion exact: PASS/PASS;
- scales exact: PASS/PASS;
- sampled dequantization maximum absolute delta: `0.0` for both projections.

This is relevant because a separate current gfx1201 GPTQ issue reports qzeros-layout failures. That failure did not reproduce with this AutoAWQ checkpoint/backport.

## Anomalies preserved, not hidden

On start 2, the first cold strict-correctness request showed a long lazy/cold TTFT and a different output hash. An immediate hot repeat returned the canonical stock hash and normal TTFT. This is treated as a cold/lazy artifact to characterize, not silently discarded.

After the canonical start-3 measurement, a later same-process measurement dropped to `145.119938 tok/s` C4 and one of the four C4 outputs changed hash. At diagnosis the R9700 was around 57 °C, the stock service remained inactive, and no competing stock VRAM consumer was present. This observation is excluded from the independent-start aggregate but remains an open stability signal.

## Interpretation

The Phase 3 repack path has now produced a reproducible **batched C4 full-model win**. It is not yet a universal serving win:

- C1 median is only about `60.367 tok/s`, below the stable stock+queue1 small-M region (~63–65 tok/s).
- ~6K-context decode median is about `55.199 tok/s`, below the clean stock+queue1 long-context median (~58.869 tok/s).
- one later same-process degradation remains unexplained.

Therefore a public statement should say **~20.8% C4 throughput improvement across three independent R9700 process starts under the tested workload**, not “20.8% faster everywhere.”

## Next optimization target

The current runtime still reports that it cannot find a tuned MoE config at:

`E=128,N=768,device_name=AMD_Radeon_R9700,dtype=int4_w4a16.json`

A current upstream GitHub code search returns no `AMD_Radeon_R9700 int4_w4a16` match. Upstream carries R9700 FP8 tuning and an INT4 W4A16 config for Radeon 8060S, but not the R9700 INT4 shape required here. This is therefore a valid HyperLoom optimization target.
